# Project Status

Last updated: 2026-09-03 (Cross-cutting bugfix — order cancellation, quote pricing/creation, deal-value sync)

Tracks progress against the 18-module Enterprise Internal System spec. Modules are built strictly in phase order — each depends on the guards/services of every module before it. This file is the living checklist; `CLAUDE.md` is the architecture/commands reference.

## Cross-cutting bugfix — status workflow enforcement (2026-08-11)

A fix pass across four existing list views (CRM Leads, CRM Deals, Sales Quotes, Employees Leave Approvals) that all shared the same underlying gaps: no server-side enforcement of valid status sequencing, and no way to change status without opening a detail page. All four now share one pattern: a small `isValidXStatusTransition`/sequence-array guard in the relevant `*.service.ts` (rejects skipped stages with a 400, same `AppException` pattern as everywhere else — audited/RBAC-checked automatically like any other mutation, no bypass), mirrored on the frontend as a `nextXStatuses(current)` helper (`features/{crm,sales,employees}/lib/transitions.ts`) that drives an inline `<Select>` in the list-view status column so only legal next states are ever offered (never "not shown" vs "disabled" ambiguity — invalid targets are simply absent from the list). Terminal states render the same `Select`, just `disabled`, for visual consistency across tabs.
- **Leads**: sequence is New → Contacted → Qualified, Lost from any non-terminal stage; CONVERTED stays reachable only via the existing `POST /crm/leads/:id/convert`, which now also requires the lead be `QUALIFIED` first (previously any non-converted status could convert). "Add lead" is now gated to the New tab only (`status === 'NEW'`) — leads never enter the pipeline anywhere else. `LeadDetailPage` gained the same inline dropdown (it previously had *no* status control at all, only a read-only badge) plus a "Mark as Lost" button and a disabled+tooltip "Convert to customer" when not yet Qualified.
- **Deals**: sequence is New → Qualified → Proposal → Negotiation → Won, Lost from any non-terminal stage. `DealDetailPage`'s old always-shows-all-6-stages `Select` was replaced with the same next-stage-only dropdown plus two named actions, `Mark as Won` (only enabled from Negotiation) and `Mark as Lost` (enabled from any non-terminal stage) — see CLAUDE.md's naming rationale below.
- **Quotes**: sequence is Draft → Sent → {Accepted, Rejected, Expired}; CONVERTED stays out of band via `POST /sales/quotes/:id/convert`, which now also requires status `SENT` or `ACCEPTED` (previously any non-converted status, including Draft, could convert). `QuoteDetailPage` gained named actions `Send Quote` (Draft→Sent), `Accept Quote`/`Reject Quote` (Sent→Accepted/Rejected) and the existing "Convert to order" button is `disabled` with a native `title` tooltip ("Send the quote before converting it to an order.") until convertible — no new shadcn Tooltip primitive was added for this; a wrapping `<span title=...>` around the disabled `<Button>` was enough since disabled elements don't reliably surface their own `title`.
- **Leave Approvals**: no schema/status changes needed here — `LeaveService.decide()` already only allowed `PENDING → APPROVED/REJECTED` (kept as the terminal-state boundary; reopening a decided request deliberately has no path through this dropdown, per the bug's "separate reopen action" note — no reopen action exists yet, out of scope). What was missing was entirely on the frontend: the list had no way to act without... actually it did have inline Approve/Reject links already, but no "View" and no detail page. Added `GET /leave-requests/:id` (`RequirePermission('employees','VIEW')`, same as the list endpoint) + `LeaveRequestDetailPage` (employee, type, date range, reason, status, `Approve`/`Reject` buttons when Pending) wired at `/leave-approvals/:id`, and swapped the list's plain Approve/Reject text links for the same inline-dropdown pattern as the other three pages.
- Button-naming convention (explicit ask): the list-view dropdown stays generically labeled "Status" everywhere (it's a fast jump-to-any-valid-next-state control); detail-view buttons that trigger one specific, consequential transition are named for what they do — `Send Quote`/`Accept Quote`/`Reject Quote`, `Mark as Won`/`Mark as Lost`, `Approve`/`Reject` — never a generic "change status" button.
- Confirmed unchanged, not a bug: `MyWorkPage`'s "no employee profile" message for a user with no linked `Employee` record — that's the correct self-service behavior tied to the logged-in user, unrelated to any of the above.
- Verified via curl (every invalid transition 400s/409s with the expected `AppException` code, every valid one succeeds) and a scripted Playwright pass through all four list+detail page pairs in the browser.
- **Follow-up pass**: two smaller gaps in the same family, fixed together. (1) `DealsPage`'s "Add deal" and `QuotesPage`'s "New quote" buttons had the identical Bug-2-for-Leads problem — visible on every stage/status tab, not just the entry one — gated the same way (`stage === 'NEW'` / `status === 'DRAFT'`). (2) `OrdersPage` had no inline status control at all (plain `Badge`, "the fourth pipeline that still needed the pattern"); added `nextOrderStatuses` to `sales/lib/transitions.ts` and the same list-view dropdown, backed by a new `isValidOrderStatusTransition` in `orders.service.ts`: PENDING → CONFIRMED → FULFILLED, with CANCELLED reachable from PENDING or CONFIRMED but not FULFILLED (both FULFILLED and CANCELLED are terminal) — replaces the old ad hoc "blocked once CANCELLED" check with the same sequence-array guard used everywhere else (the "can't cancel an already-invoiced order" business rule is unchanged, still checked separately). `OrderDetailPage`'s status `Select` previously listed all 4 statuses unconditionally (pre-dating the sequential-transition convention) — narrowed to current + valid-next-only, matching `DealDetailPage`; the control disappears entirely once an order is Fulfilled or Cancelled (no dedicated named actions exist for order status the way Quotes/Deals have, so there's nothing to fall back to but the header badge).

## Cross-cutting fix — Deal ↔ Quote/Order traceability (2026-08-20)

CRM's Deals and Sales Management's Quotes/Orders ran as two disconnected pipelines with no link between a Deal and the paperwork it produced. Fixed by adding a plain, nullable `dealId` reference — not a formal Prisma `@relation`, since Deal (CRM) and Quote/Order (Sales) are owned by different modules, matching the architecture rule's "lightweight cross-module reference" pattern already used for `Lead.assignedToUserId`/`Department.managerUserId` (migration `20260820122109_add_deal_id_to_quotes_and_orders`).

- **`Quote.dealId`** (nullable, `@@index`ed): settable on `POST /sales/quotes` and `PATCH /sales/quotes/:id` (the latter also accepts `dealId: null` to unlink). `QuotesService` validates it the same way it already validates `customerId` — via `DealsService.getDeal()` (newly injected; `SalesModule` already imports `CrmModule`, which already exports `DealsService`) — plus a new guard, `requireDealMatchesCustomer`, rejecting a deal that belongs to a different customer than the quote (`DEAL_CUSTOMER_MISMATCH`, 400) so the link can't point somewhere nonsensical.
- **`Order.dealId`** (nullable, `@@index`ed): copied from `Quote.dealId` inside `QuotesService.convertQuote()`'s existing transaction — no new validation needed there since it's inherited, not user-supplied. This keeps the full Deal → Quote → Order → Invoice chain traceable (Invoice needs no `dealId` of its own; it's reached via `Order.invoice`, already included in `OrdersService`'s responses).
- **Filtering**: `dealId` added as an optional filter on both `ListQuotesQueryDto` and `ListOrdersQueryDto` (`GET /sales/quotes?dealId=` / `GET /sales/orders?dealId=`) — the same DTO-per-route-shape pattern CLAUDE.md's pagination gotcha describes, reused rather than a new endpoint. This is also how the Deal detail page gets its data: two ordinary filtered list calls, no new backend aggregation and no CRM-reaches-into-Sales (or vice versa) violation — the same pattern `CustomerDetailPage`'s Deals tab already established for a customer-scoped list.
- **Deliberately not built** (per the request): no automatic status syncing between `Deal.stage` and `Quote`/`Order` status — this fix is link-visibility only, not behavior. `LeadDetailPage`-style "auto-advance on conversion" was not touched or extended here.
- Frontend: `QuotesPage`'s "New quote" form gained an optional "Related deal" `<Select>`, scoped to the chosen customer's deals and filtered to open ones (`stage` not `WON`/`LOST` — reusing `DealsService.getPipelineSummary()`'s own definition of "open" for consistency) unless the pre-filled deal itself is closed. `DealDetailPage`'s new "Create quote" button navigates to `/sales/quotes?dealId=&customerId=`, which `QuotesPage` reads once on mount to pre-fill and auto-open the form (then clears the query string via `setSearchParams({}, {replace:true})` so a refresh doesn't reopen it). `DealDetailPage` gained a "Quotes & orders" table (quote #/status/total, plus the linked order # and invoice # once converted, matching each row up via `Order.dealId`+`Quote.convertedToOrderId` rather than a new backend join). `QuoteDetailPage` gained a "Deal: <title>" link back to the deal, shown only when `quote.dealId` is set.
- RBAC/audit: no new permission checks — reuses the existing `sales:CREATE`/`sales:EDIT` gates on the routes the `dealId` field now rides along on, and the global `AuditLogInterceptor` captures the field like any other Quote/Order update, same as every other mutation in this system.
- Verified via curl (linked-quote create → mismatched-customer create correctly 400s `DEAL_CUSTOMER_MISMATCH` → send → convert → resulting Order carries the same `dealId` → both list endpoints correctly filter by it) and a Playwright pass through the UI (Deal detail page shows the linked Q-12/O-9 row and both links navigate correctly; Quote detail page shows and links back to the deal; "Create quote" from a Deal pre-fills customer + deal and opens the form).

## Cross-cutting feature — Flexible RBAC: multiple roles + individual employee permission overrides (2026-08-20)

A significant extension to Module 2's RBAC system, driven by an external design doc. Two findings from the "inspect first" pass the doc itself requested turned out to shrink the actual work: `User↔Role` was **already** a proper many-to-many (`UserRole` join table, `@@unique([userId, roleId])` only — no single-role constraint anywhere), and since a `Permission` row only ever represents "this role grants X" with no existing "Deny" concept, `RbacService.getUserPermissionKeys()`'s existing "union every assigned role's permission keys into one Set" was **already** Allow-wins by construction. So Sections 1-4 of the doc (multi-role support, Allow-wins combination) needed zero schema/logic changes — the only genuinely new piece was Individual Employee Permission Overrides (Sections 5-8) layered on top.

- **Schema**: `EmployeePermissionOverride` (`employeeId`, `permissionId`, `state: GRANTED|DENIED`, `@@unique([employeeId, permissionId])`) — "Inherited" is never stored, it's simply the absence of a row (spec's explicit "don't duplicate the full permission set per employee"). Formal `@relation`s to both `Employee` and `Permission` — same precedent as `UserRole`'s own existing `@relation` to `User`, a junction owned by RBAC formally relating to another module's aggregate root (CLAUDE.md: "the architecture rule is about service-layer query boundaries, not the schema graph"). Migration `20260820143231_add_employee_permission_overrides`.
- **Effective permission = role union, then overrides applied on top** (`RbacService.getUserPermissionKeys`, rewritten): Granted always adds the key, Denied always removes it, regardless of what the role union produced — implements the spec's exact priority (`Override > Role`). This is the **one** calculation consumed by both `PermissionsGuard` (backend enforcement, unchanged itself — it already just calls `userHasPermission`) and `GET /rbac/me` (frontend's permission state), so they can never disagree, per the spec's explicit "reuse the same effective-permission calculation" requirement. A user with no `Employee` profile (the bootstrap Admin) never even queries the overrides table — its access stays purely role-derived, which is what already gives Admin its full access; no special-case "is this Admin" branch needed anywhere.
- **`GET /rbac/employees/:employeeId/access`** (new): the one read endpoint the Employee detail page's Access UI needs — roles + a per-(module,action) breakdown of `roleAccess`/`override`/`effective`, built from the same two ingredients (role union, override map) as `getUserPermissionKeys`, just projected per-permission instead of collapsed into a flat key array.
- **Override mutation endpoints** (new, all under `RbacController`, `rbac:EDIT`): `PUT .../overrides/:permissionId` (`{state: GRANTED|DENIED}`), `DELETE .../overrides/:permissionId` (per-permission reset to Inherited), `POST .../overrides/reset-all` (clears every override for the employee, roles untouched). `getUserIdsWithPermission` (Notifications' "who can act on this" fan-out, from Module 14) was also updated to account for overrides — otherwise an employee individually Denied a permission would still get notified as if they could act on it, a real inconsistency the new override layer would have introduced if left alone.
- **Self-modification guard** (spec Section 13: "users cannot modify their own roles or permission overrides"): `PUT /rbac/users/:userId/roles` (existing endpoint) and all three new override-mutation endpoints reject with `CANNOT_MODIFY_OWN_ACCESS` (403) when the target equals the caller — checked both in the controller (roles) and inside `RbacService` itself (overrides), so it can't be bypassed by a future caller of the service method. Deliberately **not** applied to `EmployeesController.createEmployee`'s internal call to `setUserRoles` (assigning a brand-new employee's initial roles is a distinct one-time bootstrap action, not "modifying an existing self-assignment").
- **Employee creation now requires ≥1 role** (spec Section 2, "hard validation, not a soft warning"): `CreateEmployeeDto.roleIds` (`@ArrayMinSize(1)`); `EmployeesController.createEmployee` calls `RbacService.setUserRoles(dto.userId, dto.roleIds)` right after the profile itself is created. **Zero-role fallback for existing employees** (spec: removing an existing employee's last role is allowed, blocked only at creation) needed **no code changes at all** — Dashboard, My Work, and every employee-facing "me" endpoint (attendance/leave/payroll/performance-reviews) were already un-gated by any `@RequirePermission` (the established "no decorator = authenticated, no specific permission" self-service convention), so a zero-role employee already keeps exactly that access and nothing else, for free.
- Frontend: a new `features/rbac/` API layer (first one — RBAC previously had no frontend feature folder at all, only backend CRUD endpoints unused by any page). `EmployeesPage`'s "Add employee" form gained a required "System access" role-checklist section (submit disabled until ≥1 checked — the backend 400 is the real backstop). A new `EmployeeAccessSection` component on `EmployeeDetailPage` — roles editor (checkbox list + explicit "Save roles" button, only shown when the local selection differs from the saved one) and the full per-permission "Role access / Employee override" table (tri-state `<Select>`: Inherited/Granted/Denied, exactly per the spec's "not a checkbox" requirement) with a "Reset all overrides" button gated behind a `confirm()` dialog (same native-confirm convention this codebase already uses everywhere else, e.g. deactivate-employee, convert-quote — no `AlertDialog` primitive existed and none was added). Hidden entirely without `rbac:VIEW`; edit controls additionally disabled without `rbac:EDIT` or when viewing your own record — matching UX for a rule the backend actually enforces, not a substitute for it.
- Tests: `rbac.service.spec.ts` (13 tests, new — first coverage for `RbacService`, closing a gap the "Known gaps" list had flagged since Module 14), covering the spec's own numbered test list almost 1:1 (one/multiple/conflicting roles, Individual Grant/Deny beating role results, Inherited following current roles, role changes affecting Inherited but not explicit overrides, single/all resets, self-modification rejection, Admin-unaffected via no-Employee-profile). `permissions.guard.spec.ts` (new) covers the "no decorator = authenticated only" and "missing permission → 403 regardless of frontend" mechanics directly. `create-employee.dto.spec.ts` (new) exercises the `roleIds` hard-validation through actual `class-validator` `validate()`, the same path Nest's global `ValidationPipe` uses.
- Verified via curl end-to-end against a fresh non-admin test user/employee (two roles assigned → confirmed exact union via `GET .../access`; Denied a role-granted permission and Granted a role-absent one via override → confirmed both the JSON view *and* a direct API call as that user matched exactly, including a 403 on the denied route and 200 on the granted-only-by-override one; confirmed `rbac:EDIT`-holding user still gets `CANNOT_MODIFY_OWN_ACCESS` attempting either self-role-change or self-override; per-permission reset left other overrides untouched, Reset All cleared both and left roles intact; employee creation 400s with `roleIds` omitted or empty; removing an existing employee's last role left Dashboard/My-Work/`employees:me` reachable while a business-module route 403'd) and a full Playwright pass (Add Employee form blocks submit with no role checked, un-blocks after one is checked, created employee via the actual UI ends up with exactly that role server-side; Employee detail page's Access section renders the full role-access/override table, toggling a `<Select>` to Denied updates live, Reset All Overrides' `confirm()` flow reverts it; a zero-role employee's own logged-in session shows a sidebar with only Dashboard/My Work/Notifications and a "no widgets — ask an admin" dashboard, confirming the frontend's `hasPermission`-driven nav agrees with the backend on every route it hides).

## Cross-cutting fix — Dashboard gap for non-business-module roles (2026-08-20)

Module 16's dashboard only ever had HR/Sales/Finance widgets — an employee with a designation like Frontend Developer, Backend Developer, QA Engineer, or UI/UX Designer (none of which map to any RBAC-gated business module, and there's no project/task-tracking module in this system to source engineering-specific metrics from) saw a completely empty dashboard. Fixed by adding a universal "My work" widget group, built entirely from data the employee already has unconditional self-service access to elsewhere in the app — no new module, no new permission, no new audit logging (read-only).

- **Investigated first, found half the fix already done**: the request assumed the HR/Sales/Finance sections were gated by hardcoded role-name checks that would need converting to permission checks. They weren't — `DashboardService.getSummary()` (Module 16) already checked `rbacService.userHasPermission(userId, '<module>', 'VIEW')`, not a role name, and since the flexible-RBAC pass earlier the same day made `userHasPermission` itself combine-roles-then-apply-overrides, the business widgets were **already** automatically consistent with whatever RBAC configuration an Admin sets up. Nothing needed to change there — confirmed by re-reading the existing test suite/service rather than assuming and rewriting.
- **New `personal` section on `GET /dashboard/summary`**, added alongside (not replacing) `hr`/`sales`/`finance`, and — unlike them — **never gated by a permission check**, matching the same "no `@RequirePermission` decorator = authenticated, no specific permission" convention `/my-work` and every other self-service `/me` endpoint already uses:
  - **My Attendance Today**: `AttendanceService.getTodayRecord(employeeId)` (new, exported from `EmployeesModule` — `AttendanceService` itself wasn't exported before this).
  - **My Leave**: `LeaveService.getMyLeaveSummary(employeeId)` (new) — deliberately does **not** fabricate a leave-entitlement "balance" figure, since no allocation/entitlement model exists anywhere in this schema (Module 5 never specced one); instead returns `pendingLeaveRequests` (real, their own not-yet-decided requests) and `approvedDaysThisYear` (real, derived by summing their own approved requests' day-spans clipped to the current calendar year) — both built from data that already exists, per the fix's own scope constraint.
  - **My Upcoming Events**: `CalendarEventsService.listUpcomingForUser(userId)` (new, and `CalendarModule` had to start exporting `CalendarEventsService` — it exported nothing before this) — real events (not the synthetic holiday/leave rows `listEvents` merges in for the main Calendar view; leave already has its own sub-widget above, and a company holiday isn't really "mine") this user created or was invited to, from now onward.
  - **My Unread Notifications**: `NotificationsService.getUnreadCount(userId)` — already existed and was already exported, reused as-is.
  - A caller with no `Employee` profile at all (the bootstrap Admin) gets `attendanceToday: null` / zeroed leave counts rather than an error — resolved via a new lightweight `EmployeesService.findEmployeeIdByUserId()` (unlike the existing `getEmployeeByUserId`, doesn't throw and doesn't decrypt salary, since this only needs to know whether a profile exists). Events and notifications still populate normally for that caller either way, since both are keyed by `User`, not `Employee`.
- **Frontend**: `DashboardPage` now renders a "My work" card grid (4 cards, always present once the query resolves) above the existing "Modules" grid, which itself now only renders when non-empty (the old "No widgets to show yet — ask an admin" empty state is gone — a zero-role employee now always has the "My work" cards to look at instead of an explanatory dead end, which was the actual bug).
- Tests: `dashboard.service.spec.ts` extended (7 tests total) — the existing hr/sales/finance permission-gating tests are untouched; new tests cover `personal` being populated for a zero-permission caller, populated identically alongside a fully-permissioned caller (not an either/or), gracefully degrading attendance/leave (but not events/notifications) for a caller with no Employee profile, and reporting "no record yet" as `null` rather than a fabricated empty object.
- Verified via curl (admin, who has no Employee profile: `attendanceToday: null` + zeroed leave, but real upcoming events and a real notification count; the zero-role test employee from the flexible-RBAC pass: `hr`/`sales`/`finance` still `null` as before, but `personal` fully populated; checked that employee in via `POST /attendance/check-in` and confirmed `attendanceToday` updated on the very next summary read) and a Playwright pass in the browser confirming both screens side by side — the zero-role employee's dashboard now shows a populated "My work" grid with no "Modules" section and no dead-end message, while Admin sees "My work" *and* the full "Modules" grid together, unchanged from before.

## Cross-cutting fix — Dashboard/"My Work" account-state visibility rules (2026-09-01)

A follow-up to the Module 16 Dashboard gap fix above: that pass gave every authenticated account a populated "My work" grid, but didn't distinguish *why* an account might have nothing there. Three account states actually exist — has an Employee profile (normal case); no Employee profile but real effective permissions (e.g. Super Admin/bootstrap Admin); no Employee profile and no effective permissions at all (a self-registered account never assigned a role) — and only the first one should ever see "My Work". Driven by an external design doc's explicit three-state spec.

- **`GET /rbac/me` now also returns `hasEmployeeProfile`** (`RbacService.hasEmployeeProfile()`, reusing the same `Employee.userId` lookup `getUserPermissionKeys()` already does for overrides) — lets the frontend know both halves of the state (Employee profile + effective permissions) from the one call it already makes at login/register/bootstrap, no extra round trip and no relying on catching `/employees/me`'s 404.
- **Frontend state derivation** (`DashboardPage.tsx`): `hasEmployeeProfile` → State A; no profile but `permissions.length > 0` → State B; neither → State C. State C renders *only* the pending-setup message ("Your account is not set as an employee profile yet. Contact Admin/HR for profile setup.") and skips the `/dashboard/summary` fetch entirely (`useDashboardSummary(enabled)` gained an `enabled` param for this). State B hides the "My Work" heading/grid and relocates "Upcoming events"/"My notifications" (already User-scoped, not Employee-scoped, per the Module 16 gap fix) into the Modules grid — deliberately never an attendance widget there, since attendance has no meaning without an Employee record. State A is pixel-for-pixel unchanged.
- **Removed the "Roles & permissions" widget** from the Modules section entirely (it was `hasRole('Admin')`-gated dead UI — "Module 2 (RBAC) is live — API-only for now" — the one remaining role-name check in the whole dashboard, now gone along with the widget). Module 16's own "Admin-only 'Roles & permissions' card still present" verification note above is superseded by this.
- **`AppLayout.tsx`**: "My Work" nav item now conditional on `hasEmployeeProfile`, same as every other nav item's permission gating (previously unconditional, the only nav item with no gate at all).
- **`MyWorkPage.tsx`**: direct URL access with no Employee profile no longer renders an inline "doesn't have an employee profile" message — the nav item being hidden means the page shouldn't normally be reached, so it now redirects to `/dashboard` (`<Navigate replace>`) instead.
- No new permission bypass — this is presentation-layer only, same RBAC guards as before decide what data each widget can actually query.
- Verified via curl against three real accounts (bootstrap Admin: `hasEmployeeProfile:false` + full permission set → State B; a fresh self-registered account: `hasEmployeeProfile:false` + `permissions:[]` → State C; a newly created Employee with a role: `hasEmployeeProfile:true` → State A regardless of that role's own permission set) and a Playwright pass driving real logins for all three in the browser (screenshots confirmed State C shows only the pending message and nothing else, State B's Modules grid shows the relocated Upcoming-events/My-notifications cards with no My-Work section/nav item and no Roles & permissions card, State A unchanged including the full standalone My Work page).

## Cross-cutting bugfix — order cancellation, quote pricing/creation, deal-value sync (2026-09-03)

Four related fixes to Modules 8/9 (CRM Deals, Sales Quotes/Orders), landed together per an explicit fix prompt with exact acceptance criteria.

- **Order cancellation stale block**: `OrdersService.updateOrder` checked "does this order have *any* linked Invoice" rather than "an *active* one" — once an invoice tied to the order was Voided, cancelling the order stayed blocked forever. Fixed by including `invoice.status` in the lookup and only blocking on `status !== VOID`.
- **Quote line-item pricing is now negotiable, not catalog-locked**: `QuoteItemInputDto` gained an optional `unitPrice` override (`buildItemsData` uses `input.unitPrice ?? product.unitPrice`) — the catalog price is only ever a starting default. `taxRatePercent` stays catalog-derived only (not asked to be overridable). **New backend guard**: `updateQuote` now rejects an `items` payload once a quote is past `DRAFT` (`QUOTE_ITEMS_LOCKED`, 409) — previously nothing stopped a raw PATCH from silently rewriting a Sent/Accepted quote's contents; enforced server-side, not just hidden in the UI, matching this codebase's "RBAC/business rules enforced at the API layer" convention.
- **Quote creation moved from the Quotes page to the Deal detail page**: `QuotesPage.tsx` lost its "New quote" button and creation form entirely — it's now view-only for creation (still fully usable for viewing, Draft editing, Send/Accept/Reject, Convert to order). `DealDetailPage.tsx` gained a "Create quote" action, visible only when `deal.stage` is `PROPOSAL` or `NEGOTIATION`, opening a modal with Customer and Related Deal **pre-filled and locked** (rendered as plain text, not editable `<Select>`s) — the quote is explicitly tied to the deal it was created from, no manual re-selection possible. Reject-and-recreate (reject the Sent quote, go back to the still-Proposal/Negotiation deal, Create Quote again) is the intended path for post-send price changes — no dedicated "amend" flow was built for that, it's just the existing Reject action plus this new Create-quote entry point.
- **New shared `QuoteLineItemsEditor` component** (`features/sales/components/`) — product/quantity/unit-price rows with live client-side Subtotal/Tax/Total recalculation (`features/sales/lib/pricing.ts`'s `computeLocalSummary`, a plain-number mirror of the backend's `sales.util.ts`, used purely for the live preview — the authoritative total always comes from the server on save), used in three places: the Deal-page create-quote modal, and `QuoteDetailPage`'s new Draft-mode editing section. A quote's line items are now **directly editable on its own detail page while Draft** (add/remove/quantity/price, with a "Save changes" button) — previously the detail page was fully read-only after creation with no path to fix a Draft quote except delete-and-recreate. Once a quote is Sent or later, the same page reverts to the original read-only table.
- **Deal.value syncs to the accepted quote's total, only on Accept**: `QuotesService.updateQuote` — when a transition actually lands on `ACCEPTED` (not a redundant re-save of an already-Accepted quote) and the quote has a `dealId`, calls `DealsService.updateDeal(dealId, { value: summarizeItems(quote.items).total })` right after the quote's own update transaction. Create/Send/Reject never touch `Deal.value`; a quote rejected during negotiation has zero effect on it, confirmed by creating a second, higher-value quote on an already-accepted deal, sending and rejecting it, and checking the deal's value never moved. `DealsService` was already injected into `QuotesService` (for the `dealId`↔customer match check from the Deal↔Quote traceability fix) and already exported from `CrmModule`, so no new module wiring was needed.
  - **Audit-logging note, stated plainly rather than left implicit**: this Deal-value change is captured under the *Quote* update's own audit row (same request, `@AuditEntity('Quote')`), not as a separate `Deal`-entity row — `DealsService.updateDeal` is called as a plain internal method here, not through `DealsController`, and `AuditLogInterceptor` only fires once per HTTP request at the controller boundary. This is the exact same "generic-interceptor, one row per request" tradeoff already documented three times in this file (Lead convert → Customer, Quote convert → Order, Order → Invoice generation) — a module writing its own second audit-log call would violate the "modules never write their own audit log calls" rule, so this wasn't special-cased. If a dedicated Deal-value-change audit trail is ever needed, `request.auditBefore` (an existing, currently-unused opt-in hook on the interceptor) is the mechanism to reach for — not something built speculatively here.

The most operationally sensitive module built so far (restore overwrites the live database), so it got a design/approval pass (plan mode) before implementation, not just a straight build.
  - **Data model**: `SystemSettings` is a **new singleton**, not an extension of Module 4's `CompanyProfile` — different owning module, keeps `SettingsModule` self-contained per the cross-module rule, and is the natural home for `backupSchedule`/`backupRetentionCount`.   - **`type`/`status`/`trigger` on `BackupRecord`/`RestoreRecord` are plain `String` columns, not Postgres enum types** — the one genuinely surprising schema decision in this module, and a real bug found the hard way during end-to-end restore testing (see below): a Postgres enum type used only by these two tables still gets `CREATE`/`DROP TYPE` statements emitted into every `pg_dump` regardless of `--exclude-table`, which breaks `pg_restore --clean` against the live, deliberately-untouched tables. Migration `20260901174539_settings_backup_status_as_string` converts the columns in place (`ALTER COLUMN ... TYPE TEXT USING ... ::TEXT`, preserving existing rows) after the first migration had already created them as enums.

- `Transaction.category` is a free-text string, not a fixed enum or a managed lookup table — a deliberate scope call in the opposite direction from Module 8's fixed `DealStage` enum (income/expense categories are business-specific and open-ended, unlike deal pipeline stages, which have a natural small fixed set). The frontend offers a curated `<datalist>` per type as a soft suggestion; the API accepts anything. Revisit if reporting ever needs categories centrally managed/renamed rather than free text.
- `AuditLog.module` is derived by `AuditLogInterceptor` from the request path's first segment (e.g. `leave-requests`, `attendance`, `performance-reviews`), **not** the `MODULES` RBAC constant — several employee-domain routers live under their own top-level path even though they share the `employees` RBAC permission (`payroll` is the one exception that's now also a real RBAC slug in its own right — see Module 7). The audit-logs filter DTO takes a free-form string for this reason, and the frontend module dropdown is populated from `GET /audit-logs/modules` (distinct values actually in the table) rather than the `MODULES` constant, to stay correct as new sub-routers land.
- `payroll` is now a second RBAC permission on top of `employees` for the same Module 5 domain — a role needs `employees:VIEW` for the directory and `payroll:VIEW` to also see compensation figures. Worth folding into a cleaner permission model if Module 5 grows more of these compensation-adjacent sub-permissions (e.g. performance reviews could arguably want the same treatment).
- `Department.managerUserId` and `LeaveRequest.decidedByUserId` are plain `User` id references, not linked to `Employee` — fine for now, but worth revisiting once a module needs to *display* manager identity beyond an id.
- The frontend's language selector (top-right of the auth pages) is cosmetic only — no i18n implementation exists.
- Payroll deduction is a flat 10% placeholder (`payroll.service.ts`) standing in for real tax/benefit rules until a payroll-policy feature is scoped.
- `POST /crm/leads/:id/convert` is audited generically as `CREATE Lead` (POST → CREATE, `@AuditEntity('Lead')`) even though it also creates a `Customer` — the global `AuditLogInterceptor` logs one row per HTTP request based on the decorator, not per Prisma write, so the new customer's own creation never gets a `CREATE Customer` audit row (the `after` payload does still capture the full `{lead, customer}` object, just filed under entityType `Lead`). Same pre-existing generic-interceptor tradeoff already noted for leave-request approve/reject; not something to special-case per CLAUDE.md's "modules never write their own audit log calls" rule.
- Deal pipeline stages are a fixed enum, not the "configurable" model the original spec wording implied — a deliberate scope reduction confirmed with the user when Module 8 was built. Revisit if a real admin-configurable-stages requirement shows up later (would need a `PipelineStage` table + `Deal.stageId` FK instead of `Deal.stage` enum).
- Module 9's `Order`/`Invoice` are deliberately narrow-scoped: an `Order` can only be created via `POST /sales/quotes/:id/convert` (no standalone "create order" endpoint — matches the roadmap's "quotes → convert to orders" wording, unlike CRM's `Customer` which is also directly creatable), and an `Order` can carry at most one `Invoice` (no partial/multi-invoice billing). Revisit both if a real requirement for either shows up.
- `POST /sales/quotes/:id/convert` and `POST /sales/orders/:id/invoice` have the same generic-audit-interceptor tradeoff as `POST /crm/leads/:id/convert` (Module 8) — the created `Order`/`Invoice` doesn't get its own `CREATE` audit row, only the converting request's row (`@AuditEntity('Quote')` / `@AuditEntity('Invoice')`) with the full nested object in `after`.
- `QuotesService` is the first cross-module consumer of another module's exported service (`CrmModule`'s `CustomersService`, imported into `SalesModule`) rather than a plain unvalidated id — establishes the pattern for Modules 10+ that need to reference a `Customer` (e.g. Finance's invoicing/receivables) or a `Product` (e.g. Inventory).
- Module 12's "Mark as Purchased" receipt/invoice upload is still not wired up — it was deliberately left out when Purchasing landed since Document Management (Module 13) didn't exist yet. Module 13 is done now (`POST /documents` accepts any `entityType`/`entityId`, so `PurchaseRequest` needs zero backend changes to become a valid target) — this is a live, actionable follow-up: add an optional file input to the "Mark as Purchased" form and a `DocumentsSection entityType="PurchaseRequest" entityId={request.id}` block to `PurchaseRequestDetailPage`.
- An Asset created automatically via "Mark as Purchased" always gets `AssetCategory.OTHER_EQUIPMENT`, since `PurchaseRequestCategory.EQUIPMENT` is a single coarse bucket while `AssetCategory` distinguishes Laptop/Monitor/Phone/Other — Admin/HR corrects the specific category afterward on the asset detail page. Revisit if Purchase Requests ever need the finer-grained category up front.
- Modules 11/12's RBAC slugs are still `inventory`/`procurement` (unchanged from the original spec naming, already seeded) even though the feature/UI names are Assets/Purchasing — a deliberate choice to avoid an RBAC-slug rename/reseed for what's otherwise a pure UI/domain-model redesign. Purely internal; not visible to end users.
- Document Management's `entityType` is a free-form string, not an enum or a validated foreign key — deliberately, since it needs to attach to "any record" per spec and validating against every other module's tables would invert the dependency direction this module needs to stay decoupled (see the architecture-rule comment at the top of its schema section). In practice only `"Employee"` and `"Customer"` are wired into the frontend so far (the roadmap's third example, "project", has no backing module in this system). A typo'd `entityType` from a future integration would silently create an orphaned, never-listed document rather than erroring — acceptable for now, revisit if that ever causes real confusion.
- The "restrict to specific roles" picker on `DocumentsSection` calls `GET /rbac/roles`, which requires `rbac:VIEW` — a user with `documents:EDIT` but not `rbac:VIEW` sees an empty role list (documented in the hook itself) rather than an error. The "specific users" picker reuses the Employees list (same limitation as the Asset assignment picker in Module 11: a `User` with no `Employee` profile, e.g. the bootstrap Admin, can't be selected as a grant target through the UI even though the API has no such restriction).
- Module 14's `EMAIL`/`SMS`/`PUSH` notification channels are real and job-driven (preference-gated, queued, dispatched by `NotificationsProcessor`) but log a delivery stub instead of calling an actual provider — this system has no email/SMS/push provider integrated anywhere yet (same gap `AuthService.forgotPassword`'s `devResetToken` already stood in for). Module 19 ("transactional email provider for outbound email") is where a real provider is scoped in; once it lands, only `NotificationsProcessor`'s stub branches need to change — `NotificationsService.notify()`'s public contract and the preference-checking logic are unaffected.
- Module 14's `NotificationEventType` enum covered Leave/Purchase Request submit/decide plus a manual system announcement; Module 15 added two more (`CALENDAR_EVENT_INVITED`/`CALENDAR_EVENT_REMINDER`) confirming the extension pattern works as anticipated — a new module calls `NotificationsService.notify()` from wherever the triggering action already lives, no infrastructure changes needed. Remaining natural candidates once their owning modules exist/grow: `DOCUMENT_SHARED` (Module 13's access-grant flow), `ASSET_ASSIGNED` (Module 11), a payroll-run-completed notification (Module 5 currently only pushes a raw `payroll:completed`/`payroll:failed` WebSocket event directly from `PayrollService`, pre-dating this module, with no persisted/read-unread record of it).
- No service-layer test suite yet for `RbacService` (including `getUserIdsWithPermission`, added by Module 14 and reused by Module 15's leave/purchase-request submitted notifications) — same pre-existing gap noted above for Auth/RBAC generally; verified via curl instead for both passes.
- Module 15's header "New event" button always defaults to today's date regardless of which month the calendar grid is currently showing (only a day-cell click respects the viewed month) — a minor UX rough edge, not a correctness bug (the create form's date fields are still fully editable before submitting). Worth fixing if it causes real confusion: default to the first visible day of the currently-viewed month instead.
- Module 15's reminder/invite notifications go out on all four channels a recipient has enabled per their preferences, same as every other notification — meaning `EMAIL`/`SMS`/`PUSH` calendar reminders hit the same stub-logging gap as every other channel (see the Module 14 entry above); only `IN_APP` is a real end-to-end reminder today.
- Module 16's `dashboard:update` WebSocket signal is deliberately coarse-grained: it fires on every successful mutation under an HR/Sales/Finance route, not only on the specific mutations that actually change one of the seven displayed numbers (e.g. editing an employee's address also triggers an `hr` refetch, even though headcount/attendance/leave counts are unaffected). Traded precision for staying a single-file addition to the already-global `AuditLogInterceptor` rather than instrumenting each business service individually — acceptable since the cost of an extra background refetch is low and the summary endpoint itself is cheap. Revisit with per-field diffing only if refetch volume ever becomes a real problem.
- Module 16's Sales/Finance revenue and cash-position figures are simple current-state/this-month snapshots (no historical trend, no date-range picker) — Module 17 (Reports & Analytics) is where filterable, exportable versions of this same data are scoped in per the roadmap.
- Module 17's sales-performance report is scoped to Deals created within the selected range, not Deals *closed* within it — the schema has no `Deal.closedAt`/`actualCloseDate` field (only `expectedCloseDate`, a forecast), so "won/lost in this range" isn't distinguishable from "created in this range and later won/lost outside it." Revisit if a real "deals closed this period" requirement shows up (would need a new timestamp stamped when `stage` transitions to WON/LOST).
- Module 17's HR report headcount is a current snapshot (same as Module 16's `getHrSummary`), not date-scoped — there's no historical headcount tracking anywhere in this schema (an employee's `status` has no effective-dated history). Only attendance and leave are genuinely trended over the selected range.
- Module 17's PDF export renders tables with simple fixed-width columns and no header/row shading — serviceable for the row counts these reports currently produce, but not battle-tested against a very wide table or thousands of rows. Revisit (e.g. a table-layout library) if a report's PDF output ever needs to handle significantly more columns or rows.
- The flexible-RBAC work only built the employee-facing half (role assignment + overrides on the Employee detail page) — there is still no frontend page for the RBAC admin actions that already exist as backend endpoints (create/edit a Role, edit a Role's own permission set, create/delete permissions is fixed-catalog so N/A). `features/rbac/` currently only has `fetchRoles`/employee-access/override calls; a full Roles management page is a pre-existing gap from Module 2, not something this pass was scoped to close.
- The Employee detail page's "Module / permission access" table renders all ~72 permissions flat (no collapse/search) — fine at the current catalog size, would want grouping/filtering if the permission catalog grows substantially.
- Module 18's storage backups are plain recursive directory snapshots under `BACKUP_ROOT`, not portable single-file archives — no archiving library (`archiver`/`tar`) is installed, and a directory copy was sufficient for this internal tool. Revisit if off-site/downloadable full backups (including the storage tree, not just the DB dump) become a real requirement.
- Module 18's `pg_restore --clean --if-exists` doesn't fully reset the database to the backup's exact state — it only drops/recreates objects present in the dump, so anything created live after the backup point and absent from it is left behind (surfaced in the restore UI copy, not silent). A true from-scratch restore would need a drop-and-recreate-the-whole-database approach, deliberately avoided since it requires tearing down the app's own live connection to a named database.
- Module 18's API-key mechanism (`ApiKeyGuard`, `X-Api-Key` header) only protects one proof-of-mechanism demo route (`GET /settings/api-keys/ping`) — the real external, documented API surface Module 19 is scoped to build will reuse this same guard on its own routes rather than reinventing key validation, but no rate-limiting-per-key or scoped-permissions-per-key exists yet.
- Module 18's `MaintenanceModeGuard` 503 window during a live restore is real but was hard to observe directly in verification — a `pg_restore` against this dev-sized database completes in well under a second, faster than a manual curl-polling loop could reliably catch it mid-flight. The guard logic itself (503 everything except `/settings/backups*` while `MaintenanceModeService.isActive()`) was verified by code inspection and by confirming the maintenance window is correctly entered/exited (`setActive(true)`/`setActive(false)` around the restore call) rather than by directly observing a 503 in transit.

## Environment reference

- Bootstrap admin (seeded): `admin@enterprise.local` / `ChangeMe123!` (from `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` in `backend/.env`) — rotate before any real deployment.
- Backend: `http://localhost:3000/api/v1` · Frontend: `http://localhost:5173`.
- Module 18 backups need `pg_dump`/`pg_restore` reachable — `BACKUP_ROOT`/`PG_DUMP_PATH`/`PG_RESTORE_PATH` in `backend/.env`. This dev machine's Postgres 18 install doesn't add its `bin/` to PATH, so the two `pg_*` paths are pinned to the full `C:\Program Files\PostgreSQL\18\bin\...` location explicitly rather than left to resolve from PATH.
